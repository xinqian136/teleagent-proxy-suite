# 00 · 架构总览

## 一句话

中间层反代 = **协议翻译器** + **凭证调度器** + **能力适配器**。

很多教程只讲第一层（把 Anthropic 转成 OpenAI），但真正让它在真实环境里稳定跑起来的，
是后两层。

---

## 分层

```
┌──────────────────────────────────────────────────────────────────────┐
│ 接入层  server.js                                                     │
│  · 路由：/v1/chat/completions  /v1/messages  /v1/responses           │
│  · 鉴权：Bearer 或 x-api-key                                         │
│  · CORS：允许浏览器端直连                                            │
│  · 请求摘要记录（排查「客户端到底发了什么格式」）                      │
└───────────────────────────┬──────────────────────────────────────────┘
                            │ 统一请求体（OpenAI 格式）
┌───────────────────────────▼──────────────────────────────────────────┐
│ 能力适配层  api.js + media.js + sse.js                                │
│  · api.js    Anthropic/Responses → OpenAI；模型别名解析              │
│  · media.js  远程图片 URL → base64 data URL                          │
│  · sse.js    网关 SSE → 客户端协议（OpenAI 直传 / Anthropic 转事件流）│
└───────────────────────────┬──────────────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────────────┐
│ 调度层  pool.js + refresher.js                                        │
│  · pool.js       账号池：轮询取号、失败标记、可用性判定              │
│  · refresher.js  凭证续期：定时 + 即时 + 终止性错误分类              │
└───────────────────────────┬──────────────────────────────────────────┘
                            │ token + installId + deviceId
┌───────────────────────────▼──────────────────────────────────────────┐
│ 传输层  signer.js + gateway.js                                        │
│  · signer.js   双轮 HMAC-SHA256 签名                                 │
│  · gateway.js  构造请求头、发请求、续期 token                         │
└───────────────────────────┬──────────────────────────────────────────┘
                            │
                    ┌───────▼────────┐
                    │   云 网 关      │
                    │ agent.teleai…  │
                    └────────────────┘
```

v4 额外多了一层 **Web 管理后台**（`lib/web/`），反向代理回内部反代，
让「改端口 / 换密钥 / 扫账号」这些操作不用碰命令行。

## 一次请求的完整生命周期

以 `POST /v1/chat/completions`，`stream: true`，带一张图片为例：

```
① 接入层
   读 body → JSON.parse
   recordRequest() 记摘要：model / stream / roles / 媒体类型
   ↓
② 判断 stream
   parsed.stream === true → handleStream()
   ↓
③ 协议归一
   /v1/chat/completions  →  body 原样（不重建！）
   /v1/messages          →  api.anthropicToGateway(body)
   /v1/responses         →  api.responsesToGateway(body)
   ↓
④ 媒体预处理
   media.processBody()：远程图 → base64
   ↓
⑤ 模型解析
   api.resolveModel(model, hasImage)
   chat-flagshipAuto + 带图 → chat-flash
   ↓
⑥ 选账号
   pool.pick() → 轮询取一个可用账号
   ↓
⑦ 保鲜
   refresher.ensureFresh(rec) → token 快过期就先续
   ↓
⑧ 签名并发请求
   signer.buildHeaders() → gateway.chatCompletion({stream:true})
   ↓
⑨ 错误分支
   非 200 → extractError()
     ├─ 视觉不支持 且 带图 且 未降级 → 改 model 重试（一次）
     └─ 否则 → 返回错误
   ↓
⑩ 流式回传
   OpenAI/Responses → sse.pipeRaw()（原始字节透传，最保真）
   Anthropic        → sse.openaiToAnthropicStream()（转事件流）
   ↓
⑪ pool.reportSuccess()
```

非流式路径多一段：成功后**原样返回网关 JSON**（不重建），
只有 Anthropic / Responses 才做响应格式转换。

## 三个决定成败的设计原则

### 1. 请求体透传，不要重建

v3 之前，重建请求体会丢字段 —— `content` 块里的 `tool_result` / `image` / `input_file`
被过滤掉，工具循环断裂，模型「失忆」。

现在的做法：

```js
// lib/proxy/server.js
const gwBody = isAnthropic ? api.anthropicToGateway(body)
  : isResponses ? api.responsesToGateway(body)
  : body;                      // ← chat/completions 一律原样
```

响应同理，`chat/completions` 成功时直接 `res.end(r.text)` —— 网关给什么就是什么，
不重建就不会丢 `reasoning_content`、`usage` 细节和自定义字段。

**代价**：不能对 OpenAI 路径做字段级改写。所以需要改模型名时，
在转换完之后改顶层 `model` 字段（`finalBody.model = ...`），而不是重建整个 body。

### 2. 网关只认 OpenAI 格式的块

Anthropic 的块必须转成 OpenAI 的，否则网关报 `1214 类型错误`：

```
Anthropic                →  OpenAI
{type:'text'}             →  {type:'text'}
{type:'image', source}    →  {type:'image_url', image_url:{url}}
{type:'tool_use'}         →  assistant.tool_calls[]
{type:'tool_result'}      →  {role:'tool', tool_call_id}
{type:'document'}         →  文本说明（网关不支持文件输入）
{type:'thinking'}         →  丢弃（网关不认）
```

详见 [01 · 协议转换](01-协议转换.md)。

### 3. 网关的模型路由是动态的

同一个模型名 `chat-flagship`，今天能看图，明天可能就被路由到只支持文本的后端。
表现形式还会变 —— 可能报 `400 only supports text input`，也可能**返回 200 但模型答
「我无法查看图片」**。

所以不能只靠「检测到错误再降级」，必须有**显式模型别名**：

```
chat-flagshipAuto
  ├─ 带图片 → chat-flash      （视觉稳定）
  └─ 纯文本 → chat-flagship   （旗舰）
```

详见 [04 · 视觉与降级](04-视觉与降级.md)。

## 模块地图

以 v4 为准（`versions/v4/`）：

```
lib/
├─ proxy/          ← 反代核心
│  ├─ server.js      接入层：路由、鉴权、调度、SSE 分支
│  ├─ api.js         协议转换 + 模型别名
│  ├─ media.js       远程图 → base64
│  ├─ sse.js         流式：原始透传 / Anthropic 事件流
│  ├─ gateway.js     上游请求 + 渠道密钥解析 + token 续期接口
│  ├─ signer.js      双轮 HMAC 签名
│  ├─ pool.js        账号池
│  ├─ refresher.js   凭证续期
│  └─ client-config.js 生成各客户端的配置片段
├─ account-manager/ ← 账号生命周期
│  ├─ scanner.js     扫本机数据目录，解 safe_storage / local 密文
│  ├─ model.js       账号记录模型 + 可用性判定
│  ├─ exporter.js    导出 bundle / xlsx / csv
│  └─ importer.js    导入 bundle
├─ storage/         ← 存储层
│  ├─ json-store.js  加密 JSON（默认）
│  ├─ sqlite-store.js SQLite（需 Node 22+）
│  └─ index.js       按配置选择
├─ web/             ← Web 管理后台
│  ├─ server.js      路由：/ 界面、/api/admin/* 管理、/v1/* 反代
│  ├─ manager.js     反代生命周期（热启停）
│  ├─ settings.js    设置持久化
│  └─ public/        零构建单页前端
├─ crypto.js         AES-256-GCM + scrypt 口令派生
└─ dpapi.js          Windows DPAPI 解密（拿 safeStorage 的 AES key）
```

## 端口与进程模型

| 版本 | 反代端口 | Web 端口 | 进程模型 |
|---|---|---|---|
| v1 | 8788（内核链路）/ 8790（直连） | — | 两个独立 shim |
| v2 | 8792 | — | 单进程 |
| v3 | 8792 | 8795 | Web 与反代同进程 |
| v4 | 8793 | 8796 | Web 与反代同进程 |

v3/v4 刻意让 Web 后台和反代**跑在同一个进程**：

> 反代服务与 Web 后台在同一个进程里，Web 关了反代也关 —— 这是有意的：
> 避免两个独立进程各管一份凭据、互相踩。

反代可热启停（改端口 / API Key → 内部 restart），但整个后台只有一个进程。
