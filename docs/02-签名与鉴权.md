# 02 · 签名与鉴权

网关不认裸请求。每次调用都要带一整套 `X-SuperAgent-*` 头，其中
`X-SuperAgent-Signature` 是**双轮 HMAC-SHA256** 算出来的。

源码：`versions/v4/lib/proxy/signer.js`、`versions/v4/lib/proxy/gateway.js`

---

## 1. 完整请求头

```
POST https://agent.teleai.com.cn/superCowork/sapi/api/v1/chat/completions

Authorization: Bearer sk-<渠道密钥>          ← 通道密钥，所有用户共用
X-Token: <tenant>:<JWT>                       ← 用户登录态
X-Route-Target: ops-gateway
X-Runtime-Env: ctyun_pc
X-App-Version: 3.1.0
X-SuperAgent-Timestamp: <10 位秒>
X-SuperAgent-Nonce: <uuid v4>
X-SuperAgent-Device-Id: <deviceId>
X-SuperAgent-Install-Id: <installId>
X-SuperAgent-Sign-Version: v1
X-SuperAgent-Signature: <64 位小写 hex>
User-Agent: super-agent/1.0
Content-Type: application/json
Accept: text/event-stream
```

**头名是大写 A**：`X-SuperAgent-*`，不是 `X-Superagent-*`（2.5.0 的写法，3.x 已改）。

---

## 2. 签名算法

密钥 `K` = JWT 的**第三段**（签名段）。

```
第一轮（5 段，分隔符 "/"）：
  m1   = "superagent-auth-v1/{token}/{installId}/{ts}/{nonce}"
  sig1 = hex( HMAC_SHA256(K, m1) )

第二轮（7 段，分隔符 "\n"）：
  m2   = "superagent-auth-v1\n{METHOD}\n{path}\n{ts}\n{nonce}\n{appVersion}\n{bodyHash}"
  sig  = hex( HMAC_SHA256(sig1, m2) )

  bodyHash = hex( SHA256(body 原始字节) )
```

代码：

```js
function computeSignature(o) {
  const K = jwtThirdSegment(o.token);
  const bodyBuf = Buffer.isBuffer(o.body) ? o.body : Buffer.from(o.body || '', 'utf8');
  const bodyHash = sha256Hex(bodyBuf);
  const ts = String(o.ts);

  const m1 = [SCHEME, o.token, o.installId, ts, o.nonce].join('/');
  const sig1 = hmacHex(K, m1);

  const m2 = [SCHEME, String(o.method).toUpperCase(), o.path, ts, o.nonce, o.appVersion, bodyHash].join('\n');
  return hmacHex(sig1, m2);
}
```

### 五个必踩的坑

| 坑 | 正确做法 | 错的表现 |
|---|---|---|
| scheme 大小写 | 全程小写 `superagent-auth-v1` | `40104` 签名无效 |
| `ts` 单位 | **秒**，不是毫秒 | `40104` |
| bodyHash 的对象 | **实际发出的 body 字节**（含空格和字段顺序） | `40104` |
| `path` 内容 | `/superCowork/sapi/api/v1/chat/completions`（不含 query） | `40104` |
| 输出编码 | 小写 hex | `40104` |

**bodyHash 必须对应真正发出去的字节。** 最常见的错误是：
签名时算的是 `JSON.stringify(obj)`，但实际发出去时又 stringify 了一次，
或者中间经过了对象重建导致字段顺序变了。

本项目的做法是**只 stringify 一次**，同时用于签名和发送：

```js
const payload = JSON.stringify(o.body);
const headers = buildHeaders({ ..., body: payload });   // 同一个字符串
await fetch(url, { method:'POST', headers, body: payload });
```

### nonce 不可重用

服务端记录 nonce，重复使用返回 `40105`。每次请求必须生成新的：

```js
const nonce = crypto.randomUUID();
```

### appVersion 只校验格式

服务端只检查 `x.y.z` 的形式，不校验具体版本值。但它**参与签名**，
所以请求头里的值必须和签名时用的值一致。

## 3. 取 JWT 第三段

token 的格式是 `<tenant>:<JWT>`，JWT 是三段 base64url：

```js
function jwtThirdSegment(token) {
  const t = String(token);
  const i = t.indexOf(':');
  const jwt = i >= 0 ? t.slice(i + 1) : t;
  const seg = jwt.split('.');
  if (seg.length < 3) throw new Error('token 格式异常，取不到 JWT 第三段');
  return seg[2];
}
```

> 注意：`seg[2]` 拿到的字符串是 base64url 编码的，**直接当 HMAC 密钥用**，
> 不要 base64 decode —— 实测用原始字符串才与服务端一致。

## 4. 渠道密钥

`Authorization: Bearer sk-xxx` 里的那个 `sk-`，叫**渠道密钥**。
它硬编码在 TeleAgent 的 `app.asar` 里，**所有用户共用**。

两条获取路径（`gateway.resolveChannelKey()`，优先级从高到低）：

```
① 环境变量 TA_CHANNEL_KEY
② config/channel-key.txt 或 data/channel-key.txt
   ← 打包迁移时带上这个文件，目标机就不用装 TeleAgent
③ 本机 app.asar 扫描
```

从 asar 里提取的实现是**分块扫描**，因为 app.asar 有 ~981MB，
一次性读进内存会炸：

```js
const CHUNK = 1 << 22;                    // 4MB
let pos = 0, tail = '';
while (true) {
  const n = fs.readSync(fd, buf, 0, CHUNK, pos);
  if (n <= 0) break;
  const s = tail + buf.toString('latin1', 0, n);
  const m = s.match(/sk-[A-Za-z0-9]{20,32}/g);
  if (m) return m[0];
  tail = s.slice(-64);                   // 保留尾巴，防止跨块截断
  pos += n;
}
```

> `tail` 保留 64 字节是必须的 —— 密钥可能正好跨块边界。
> 用 `latin1` 读（不是 utf8）避免多字节字符把偏移搞乱。

## 5. 设备指纹

`X-SuperAgent-Device-Id` 和 `X-SuperAgent-Install-Id`：

- `deviceId`：12 位十六进制（6 字节随机），格式与 TeleAgent 一致
- `installId`：UUID v4

**每台机器本地随机生成，不复用原机器的。** 原因：

> 服务端不校验指纹（已实测全随机仍 200），
> 同一账号在多台机器上用时，服务端看到的是不同客户端，不触发同设备关联。

```js
function generateDeviceId() {
  return crypto.randomBytes(6).toString('hex');
}
```

## 6. 错误码语义

| code | 含义 | 处理 |
|---|---|---|
| 200 | 成功 | — |
| 40101 | missing super agent security headers | 缺头 / 头名大小写错 |
| 40104 | invalid signature | 算法、段序、时间戳、bodyHash 任一出错 |
| **40105** | 疑似攻击（风控） | **立刻停手**，别再重试 |
| 40109 | current user is banned | 账号被封 |
| 403 | 内容审核 / 权限不足 | 换措辞（见下） |
| 40112 | MISSING_ACCESS_TOKEN | 终止 → 需重登 |
| 40113 | SIGNATURE_INVALID | 终止 → 需重登 |
| 40114 | TOKEN_EXPIRED | **可续期** |
| 40115 | SESSION_NOT_FOUND | 终止 → 需重登 |
| 40116 | SESSION_ABSOLUTE_EXPIRED | 终止 → 需重登（90 天硬期限） |
| 1214 | type 类型错误 | Anthropic 块没转成 OpenAI 格式 |
| 1210 | 图片格式错 | 网关只吃 base64，远程 URL 要转 |
| 50005 | TEMPORARILY_UNAVAILABLE | 可重试 |

### 40104 vs 40105 是两回事

- 单个 `40104` = **你的算法不对**，无害
- **连续大量** 40104/40105 才会被判定为攻击

> 调试时**每次只发一个请求**。别批量试、别并发压测。
> 风控是累计计数的，连续错误签名的试探会推高风险分。

### 403 是内容审核

直连网关**没有内容审核记录**（走内核链路时有），某些措辞会被网关侧拦：

```
"请调用工具 get_weather 查询北京天气"           → 403
"Use the get_weather tool for city Beijing"     → 200
```

这是平台的内容安全策略，**不是协议问题**。换个措辞即可。

## 7. token 续期接口

```
POST https://agent.teleai.com.cn/superCowork/sapi/cowork/auth/token-refresh

X-Token: <旧 token>
X-Timestamp: <秒>
X-Nonce: <uuid>
X-App-Version: 3.1.0
X-OS-Type: Windows
X-SuperAgent-Device-Id: <deviceId>
```

**注意这个接口不需要签名** —— 它是续期接口本身，
用旧 token 证明身份就够了。

响应里取 token：

```js
const at = json?.data?.accessToken || json?.accessToken;
```

> 续期会**轮转 session**：拿到新 token 必须立刻落盘。
> 写回失败要保留旧 token 降级（宁可晚点死，也不能把链子彻底断掉）。
> 详见 [03 · 凭证与账号池](03-凭证与账号池.md)。

## 8. 自己实现时的检查清单

- [ ] `ts` 用秒
- [ ] nonce 每次新生成，不复用
- [ ] bodyHash 算的是**真正发出去的字节**
- [ ] scheme 全小写
- [ ] 头名 `X-SuperAgent-*` 大写 A
- [ ] `X-Token` 是 `<tenant>:<JWT>` 完整形式，不是光 JWT
- [ ] `Authorization` 用渠道密钥，不是用户 token
- [ ] 输出小写 hex
- [ ] 调试时一次只发一个请求
