# 09 · 版本演进史

每个版本解决什么问题、踩了什么坑、为什么这么改。
**这是整个项目最有价值的部分** —— 代码可以抄，演进逻辑抄不走。

---

## 时间线

```
v1  两条链路的原型
     ├─ 方案 B：走 TeleAgent 内核（4397）—— 风险低，但不支持自定义 tools

     ↓
```

## v1 · 双链路原型

**4 个提交，最早的一版。**

### 核心决策：两条链路

| | 方案 B（8788） | 方案 A（8790） |
|---|---|---|
| 链路 | shim → **TeleAgent 内核** → 云网关 | shim → **云网关**（直连） |
| 出站请求由谁发出 | **App 进程** | 你的 shim |
| 服务端看到的客户端 | 就是 App | 「第二客户端」 |
| 自定义 tools | ❌ 内核忽略 | ✅ **原生支持** |
| 封号风险 | **低** | **较高** |

这个选择很关键：

> 走内核链路时，流量和真人用 App 无法区分，服务端看到的就是官方客户端。
> 直连则是「第二客户端」，特征明显。

**但两条链路不能兼得**：内核跑自己的 agent loop，会忽略调用方传入的 `tools` 定义。
要接 Cline / Cursor 这类「agent 自己控制工具循环」的框架，只能直连。

### v1 的技术遗产

**方案 A 的签名算法**（逆向自 Go 内核 `einoprovider.(*GatewaySigner).Sign`）：

```
第一轮（5 段，分隔符 "/"）：
  m1   = "superagent-auth-v1/{token}/{installId}/{ts}/{nonce}"
  sig1 = hex( HMAC_SHA256(K, m1) )

第二轮（7 段，分隔符 "\n"）：
  m2   = "superagent-auth-v1\n{METHOD}\n{path}\n{ts}\n{nonce}\n{appVersion}\n{bodyHash}"
  sig  = hex( HMAC_SHA256(sig1, m2) )
```

这个算法一直沿用到 v4。详见 [02 · 签名与鉴权](02-签名与鉴权.md)。

**sessionKey 提取**（方案 B 专用）：

3.0.1 起 sessionKey 不在进程环境块里了（改走 stdin 传给 Go 内核，进程 env 被主动清理），
所以扫环境的老办法失效。新做法是扫内存找「43 字符 base64url 且解码后正好 32 字节」的候选，
逐个按 `local-v1` 协议签名调内核 `/provider`，返回 200 的那个就是真的。

端到端校验，零误判。约 1-3 分钟。

**逆向工具链**（`_re/tools/`）：

| 工具 | 用途 |
|---|---|
| `gofuncs/main.go` | 用 `debug/gosym` 提取 Go 二进制符号表 |
| `go-disasm.py` | capstone 反汇编指定函数 |
| `go-refs.py` | 提取 `lea reg,[rip+disp]` 指向的字符串 |
| `find-str.py` | 扫内存找字符串，区分 IMAGE 段与堆 |
| `heap-ctx.py` | 堆上找字符串并打印邻近内容 |
| `dump-json.py` | 从内存提取完整 JSON 配置 |
| `wire-headers.py` | 扫内存找 HTTP 头名 |

踩过的坑（都写在 `SCHEME-A-B.md` 里）：

- **itab 地址**：itab 头是 24 字节（inter/type/hash），`fun[0]` 在 **+24**。
  算错会导致「函数是死代码」的误判。
- **Go PE 的 pclntab 在 .rdata**，不是 .text；`textStart` 常为 0，要用 .text 段 RVA 兜底。
- **`gofuncs.exe` 不传正则只输出前 40 条**，要传 `.*`。
- **内核进程的环境变量**能从内存里挖到（`OPENCODE_TOOLS_PROVIDER_CONTENT` 等），
  里面有 provider 的 baseURL / apiKey / headers —— 这是还原鉴权的捷径。

### v1 的局限

- 视觉（`image_url`）不支持
- 流式是伪流式（内核一次性返回后分块模拟）
- 账号是硬编码的单个 token，没有池化
- 每次重启要重新提取 sessionKey

## v2 · 模块化重写

**3 个提交。**

v1 的问题是「能用但不能长期跑」：凭证会过期、不能用多账号、换个机器要重头搞。

### 核心改动

**① 账号池**

```js
pick() {
  const list = this.usable();
  if (!list.length) return null;
  const r = list[this._cursor % list.length];   // 轮询
  this._cursor = (this._cursor + 1) % list.length;
  return r;
}
```

**② 凭证自续期**

三层触发：定时（6h）/ 请求前 / 请求失败后立即。
错误分类：

```
终止（需重登）：40112  40113  40115  40116
可重试：        40114  50005  40105
```

**③ 加密存储 + 可迁移**

加密 JSON（默认）/ SQLite（Node 22+）。
bundle 导出包含 token + 渠道密钥 → 目标机不用装 TeleAgent。

**④ 账号扫描改扫数据目录**

v1 早期扫安装位置，v2 改成扫 `%USERPROFILE%\.local\share\TeleAgent\users\v1_public_*`。
commit `dad186e` 专门记了这个改动。

**⑤ 一键化**

```cmd
启动.cmd / 导出账号.cmd / 导入账号.cmd / 检查状态.cmd
```

「别再记命令」。

### v2 的意义

v2 是**第一个能长期跑的版本**。架构定型：分层（proxy / account-manager / storage），
后面 v3 v4 都在这个骨架上长。

## v3 · Web 后台 + 修三个真 bug

**11 个提交。这个版本信息量最大。**

### ① Web 管理后台（`02b1e0b`）

所有操作网页点：扫账号、导入导出、启停反代、改设置、看日志。

三个设计点：

- **单进程三路由**：`/` 界面、`/api/admin/*` 管理、`/v1/*` 反代
- **反代可热启停**：改端口 / API Key → 内部 restart
- **反代与后台同进程**：避免两个进程各管一份凭据互相踩

暂停/恢复分三种粒度（`a7c9c3c`），其中「暂停」是**持久化**的，
重启后台也不会自动起反代。

### ② 修复：stream:true 被吞（`31e3dea`）

**这是 v3 最重要的修复。**

> 复杂任务失败 —— 根因是吞掉了 stream:true

表现：简单请求正常（客户端有超时兜底），复杂任务（几分钟）客户端先超时断开。
根因是反代重建请求体时把 `stream` 字段丢了。

修法：

```js
if (parsed.stream === true) {
  return await handleStream(url, parsed, res);
}
```

并且流式分支里强制 `gwBody.stream = true`。

**教训**：请求体透传，别重建。详见 [01 · 协议转换](01-协议转换.md)。

### ③ 修复：Anthropic 图片/工具结果全失效（`9b56b14`）

网关只认 OpenAI 格式的块。Anthropic 的 `image` / `tool_use` / `tool_result` 直接发过去，
网关报 `1214 类型错误`。

修法是完整的块映射表 —— 见 [01 · 协议转换](01-协议转换.md)。

**教训**：多协议适配不是「改个字段名」，是「每个块类型都要映射」。

### ④ 新增：远程图 URL → base64（`b3d25c9`）

网关只吃 base64，客户端传的是签名 URL。加了 `media.js`。

### ⑤ 试错：远程图缓存，加了又撤回（`41044e0` → `c4a45dc`）

```
41044e0  perf: 远程图加缓存 —— 长会话里同一批图被反复下载
c4a45dc  revert: 撤回远程图缓存（用户反馈加了之后图片失效）
```

**这是整个项目最有价值的一次回滚。**

用户的原话是「改了之后不行了不能看图了，赶紧改回去」。
事后分析表明：根因不是缓存，而是**网关模型路由的变化**。

两个结论：

1. **图片相关逻辑的改动风险很高，回滚成本远大于收益。**
   缓存带来的收益（省几秒延迟）远小于风险。
2. 真正的解法是**模型别名**（v4），不是缓存。

### ⑥ 修复：非流式请求全 500（`34b06f9`）

```js
recordResponse(pathname, ...)     // ← 形参叫 pathname
recordResponse(url, ...)          // ← 调用传的是 url
```

`pathname` 未定义 → ReferenceError → catch 兜底成 500。

**教训**：这类 bug 很蠢但很致命，而且只在非流式路径触发（流式路径参数名恰好一致）。
写完最好每个分支都单独测一遍。

### ⑦ 验收脚本（`f2eb15d`）

`scripts/test-full.js`，13 项全功能验收。
**这个提交是 v3 的稳定基线** —— 后面 v4 从 `80bc575` 派生（v3 的某个中间点）。

### ⑧ install-task.cmd 探测自带 node（`4065c69`）

计划任务里要找到可用的 node.exe：系统 PATH 的，或 TeleAgent 自带的
`%USERPROFILE%\.local\share\TeleAgent\runtimes\node\node.exe`。

## v4 · 视觉自动降级 + 模型别名

**3 个提交，从 v3 的 `80bc575` 派生。**

### ① 视觉自动降级（`c0d3d61`）

检测到「模型不支持视觉」的错误 → 换 `chat-flash` 重试。

```js
const VISION_FALLBACK_MODEL = 'chat-flash';

function isVisionUnsupported(err) {
  const m = String((err && err.message) || '');
  return /only supports text input/i.test(m)
    || /not a VLM/i.test(m)
    || /\b20041\b/.test(m)
    || /unsupported content type 'image/i.test(m);
}
```

### ② 模型别名 `chat-flagshipAuto`（`e16dd19`）

**这一版最重要的改动。**

原因：网关的模型路由是动态的，同一个模型名有时支持视觉、有时被路由到只支持文本的后端。
表现形式还会变 —— 可能报 `400`，也可能**返回 200 但模型答「我无法查看图片」**。

> 靠检测错误再降级不可靠 —— 报错形式会变。

所以要有**显式映射**：

```
chat-flagshipAuto
  ├─ 带图片 → chat-flash      （视觉稳定）
  └─ 纯文本 → chat-flagship   （旗舰）
```

客户端只管选 `chat-flagshipAuto`，不用关心网关当天怎么路由。
带图用哪个模型可在「设置」页改。

### ③ 端口隔离

v4 反代 8793 / Web 8796，v3 是 8792 / 8795，**刻意错开**。
计划任务名也不同（`TeleAgent Proxy V4`）。

> v3 与 v4 不要同时跑同一个账号 —— 同一 token 两处用，有封号风险。

| 场景 | 选 |
|---|---|
