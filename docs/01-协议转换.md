# 01 · 协议转换

三种客户端协议，一套上游格式。转换层是整个项目最容易出 bug 的地方 ——
**丢一个字段，模型就开始失忆或工具循环断裂**。

源码：`versions/v4/lib/proxy/api.js`

---

## 0. 先说结论：网关只吃 OpenAI

上游网关的 `/chat/completions` 只接受 **OpenAI Chat Completions** 格式，
且实测只支持两种输入块：

- `{type:'text', text}`
- `{type:'image_url', image_url:{url}}`，且 `url` 必须是 **base64 data URL**

其他协议进来必须转。而且**转的时候不能丢东西**。

---

## 1. 三套协议速览

| | OpenAI Chat Completions | Anthropic Messages | OpenAI Responses |
|---|---|---|---|
| 端点 | `/v1/chat/completions` | `/v1/messages` | `/v1/responses` |
| 消息数组 | `messages` | `messages` | **`input`** |
| system | `messages[0].role='system'` | **顶层 `system`** | **顶层 `instructions`** |
| 文本块 | `{type:'text',text}` | `{type:'text',text}` | `{type:'input_text',text}` |
| 图片块 | `{type:'image_url',image_url:{url}}` | `{type:'image',source:{...}}` | `{type:'input_image',image_url}` |
| 工具定义 | `tools[].function` | `tools[].input_schema` | `tools[].function` 或 `tools[].flat` |
| 工具调用 | `assistant.tool_calls[]` | content 块 `{type:'tool_use'}` | `{type:'function_call'}` |
| 工具结果 | `{role:'tool',tool_call_id}` | content 块 `{type:'tool_result'}` | `{type:'function_call_output'}` |
| 流式 | `data:` 增量 | `event:` 事件序列 | `data:` 增量 |
| 鉴权头 | `Authorization: Bearer` | `x-api-key` | `Authorization: Bearer` |

> Anthropic 的 `system` 是**顶层字段**，Responses 的 system 是 `instructions` ——
> 这两个最容易漏，漏了就是「模型完全不知道你的系统提示」。

---

## 2. Anthropic → OpenAI（重点）

`api.anthropicToGateway(body)`

### 2.1 一条消息可能变成多条

Anthropic 把工具调用和工具结果都塞在 `content` 数组里，OpenAI 分开放：

```
Anthropic assistant 消息:
  content: [ {type:'tool_use', id:'tu_1', name:'read', input:{path:'a.txt'}} ]

→ OpenAI:
  { role:'assistant', content:'', tool_calls:[
      {id:'tu_1', type:'function',
       function:{name:'read', arguments:'{"path":"a.txt"}'}} ] }
```

```
Anthropic user 消息:
  content: [ {type:'tool_result', tool_use_id:'tu_1', content:'文件内容'} ]

→ OpenAI:
  { role:'tool', tool_call_id:'tu_1', content:'文件内容' }
```

**顺序很重要**：工具结果先于同一条消息的文本输出（对应 OpenAI 的 tool → user 顺序）。

### 2.2 块类型映射表

| Anthropic 块 | OpenAI 结果 | 备注 |
|---|---|---|
| `text` | 文本 | 直接拼进 content |
| `image` + `source.type='base64'` | `{type:'image_url',image_url:{url:'data:<mime>;base64,<data>'}}` | base64 直接包 data URL |
| `image` + `source.type='url'` | `{type:'image_url',image_url:{url}}` | 远程 URL 后续由 media.js 转 base64 |
| `tool_use` | `assistant.tool_calls[]` | `arguments` 是 **JSON 字符串** |
| `tool_result` | `{role:'tool',tool_call_id,content}` | content 必须是**字符串** |
| `document` | 文本说明 | 网关不支持文件输入，降级 |
| `thinking` | **丢弃** | 网关不认这个块 |
| 未知块 | `[<type> 块已忽略]` | 留个痕迹，别静默吞 |

### 2.3 工具结果的 content 必须是字符串

Anthropic 允许 `tool_result.content` 是数组。OpenAI 的 tool 消息只收字符串：

```js
function toolResultText(content) {
  if (typeof content === 'string') return content;
  if (Array.isArray(content)) {
    return content.map((c) => {
      if (typeof c === 'string') return c;
      if (c.type === 'text') return c.text || '';
      if (c.type === 'image') return '[工具返回了图片，网关暂不支持]';
      return '';
    }).filter(Boolean).join('\n');
  }
  if (content == null) return '';
  return JSON.stringify(content);
}
```

### 2.4 tool_use + 图片同时出现

这是个边界情况。Anthropic 一条 assistant 消息可以同时有 `tool_use` 和 `image`。
OpenAI 的 assistant 消息只能二选一（要么纯 content，要么 tool_calls）。

处理方式：content 用数组放图片，tool_calls 挂在同一条消息上：

```js
out.push({ role, content: [{ type:'text', text }, ...mediaParts] });
if (toolCalls.length && mediaParts.length) {
  out[out.length - 1].tool_calls = toolCalls;
}
```

## 3. Responses → OpenAI

`api.responsesToGateway(body)`

### 3.1 input 的两种形态

```js
// 字符串
body.input = "帮我写个函数"
→ { role:'user', content:'帮我写个函数' }

// 数组
body.input = [ {role:'user', content:[{type:'input_text',text:'...'}]} ]
→ { role:'user', content:[{type:'text',text:'...'}] }
```

### 3.2 块类型

| Responses 块 | OpenAI 结果 |
|---|---|
| `input_text` | `{type:'text',text}` |
| `input_image` | `{type:'image_url',image_url:{url}}` |
| `input_file` | 文本说明（网关不支持文件输入） |
| 其它 | **原样保留** |

### 3.3 tools 的三种形态

Responses 的工具定义比 OpenAI 多了种 `flat` 写法，统一成 `function`：

```js
out.tools = body.tools.map((t) => {
  if (t.type === 'function' && t.function) return t;        // 已是标准格式
  if (t.type === 'function' && t.name) {                    // 扁平格式
    return { type:'function', function:{
      name:t.name, description:t.description||'',
      parameters:t.parameters||{type:'object',properties:{}} } };
  }
  if (t.type === 'function' && t.flat) {                    // flat 嵌套
    return { type:'function', function:{
      name:t.flat.name, description:t.flat.description||'',
      parameters:t.flat.parameters||{type:'object',properties:{}} } };
  }
  return t;
});
```

### 3.4 instructions 漏了 = 模型失忆

`instructions` 是 Responses 的 system。不转的话网关收到的是**空消息列表**，
模型完全不知道上下文 —— 表现是「模型答非所问」而不是报错，最难查。

---

## 4. OpenAI 路径：原样透传

`/v1/chat/completions` 的请求体**完全不转换**：

```js
const gwBody = isAnthropic ? api.anthropicToGateway(body)
  : isResponses ? api.responsesToGateway(body)
  : body;              // ← 原样
```

理由见 [00 · 架构总览](00-架构总览.md) 的「请求体透传」。

唯一改动的是顶层 `model`（模型别名映射后），以及 media.js 对图片块的替换。

## 5. 响应方向

### 5.1 网关 → OpenAI

**不转换**，原样返回网关的 JSON。原因同样：重建会丢 `reasoning_content`、
`usage` 细节、自定义字段。

```js
if (!isAnthropic && !isResponses) {
  return { status: 200, raw: r.text };   // ← 原样
}
```

### 5.2 网关 → Anthropic

`api.gatewayToAnthropic(gw, reqModel)`：

```
网关 OpenAI 响应                     →  Anthropic 响应
{choices[0].message.content}         →  content:[{type:'text',text}]
{choices[0].message.reasoning_content}→  content:[{type:'thinking',thinking}]
{choices[0].message.tool_calls[]}    →  content:[{type:'tool_use',id,name,input}]
finish_reason:'tool_calls'           →  stop_reason:'tool_use'
usage.prompt_tokens                  →  usage.input_tokens
usage.completion_tokens              →  usage.output_tokens
```

`tool_calls[].function.arguments` 是 JSON 字符串，要 parse 成对象：

```js
input: safeParse(t.function?.arguments)   // 解析失败退回 {}
```

### 5.3 网关 → Responses

`api.gatewayToResponses(gw, reqModel)`：

```
{choices[0].message.content}          →  output:[{type:'message',content:[{type:'output_text',text}]}]
{choices[0].message.reasoning_content} →  output:[{type:'reasoning',summary:[{type:'summary_text',text}]}]
{choices[0].message.tool_calls[]}     →  output:[{type:'function_call',call_id,name,arguments}]
```

注意 Responses 的工具调用 `arguments` **保持字符串**，不 parse。

## 6. 透传字段白名单

有些字段不该转换但要原样带过去。`api.PASSTHROUGH`：

```js
const PASSTHROUGH = [
  'tools', 'tool_choice', 'parallel_tool_calls', 'max_tokens', 'max_completion_tokens',
  'temperature', 'top_p', 'top_k', 'stop', 'seed', 'n', 'presence_penalty',
  'frequency_penalty', 'logprobs', 'top_logprobs', 'response_format',
  'reasoning_effort', 'modalities', 'user', 'metadata', 'logit_bias',
  'min_p', 'top_a', 'include_reasoning', 'thinking', 'service_tier',
  'safety_identifier', 'prompt_cache_key', 'verbosity',
];
```

**白名单而非黑名单**是刻意的：客户端（尤其是新版本 SDK）会不断加新参数，
黑名单一定会漏。白名单漏了也不会「静默出错」，因为 OpenAI 路径根本不转换。

> ⚠️ 白名单漏一个字段的表现是「参数被静默忽略」——
> 比如 `temperature` 没带过去，模型输出变得更随机，但没有任何报错。

## 7. 自测：怎么验证转换对了

v3/v4 仓库里有验收脚本：

```cmd
cd versions\v4
node scripts\test-full.js     # 13 项全功能验收
node scripts\test-web.js      # 30 项 Web 后台回归
```

自己写转换层时，对应的验证点：

1. **纯文本一问一答** —— 最基本的通路
2. **带图片问「图里有什么」** —— 验证图片块没丢
3. **带 tools 的完整工具循环** —— 验证 tool_calls / tool_result 映射
4. **`stream: true`** —— 验证流式分支
5. **Anthropic 协议走一遍以上全部** —— 转换层最容易在这里出问题
